### <a name="_qmphm5d6rvi3"></a>**Решение**

[Диаграмма контекста](https://github.com/antonJagupov/architecture-standart/blob/develop/Task3/context.png)

[Диаграмма контейнеров](https://github.com/antonJagupov/architecture-standart/blob/develop/Task3/container.png)

Архитектурные решения:

1.Введение Сервиса депозитов как оркестратора процесса:
Изолирует АБС от прямой нагрузки
Кэширует справочники для ускорения
Обеспечивает единую точку интеграции для всех каналов

2.Асинхронная интеграция с АБС:
Использование RabbitMQ для очередей сообщений
Буферизация запросов в пиковые нагрузки
Гарантированная доставка команд в АБС

3.Кэширование данных:
Redis для хранения актуальных ставок
Кэширование справочников в сервисе депозитов
Синхронизация кэша при изменении данных в АБС

4.Технологический выбор:
Сервис депозитов на Java Spring Boot (совместимость с кол-центром)
MS SQL для временного хранения заявок
REST API для синхронных, RabbitMQ для асинхронных взаимодействий

5.Обоснование выбора технологий:
Java Spring Boot - наличие экспертизы в команде кол-центра, богатая экосистема
RabbitMQ вместо Kafka - совместимость с текущими стеками, достаточная функциональность для MVP
Redis - низкая latency кэширования, поддержка кластеризации
REST API - стандартный подход, понятный всем командам


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

Альтернатива 1: Прямая интеграция каналов с АБС
Плюсы: Быстрая реализация, меньше промежуточных компонентов
Минусы: Нарушение требования по нагрузке на АБС, риск недоступности банковских операций

Альтернатива 2: Полная микросервисная архитектура
Плюсы: Высокая масштабируемость, независимость сервисов
Минусы: Сложность реализации в сроки MVP, требуются новые компетенции

Альтернатива 3: Использование готового решения подрядчика
Плюсы: Быстрый вывод функционала, снижение рисков разработки
Минусы: Высокая стоимость, зависимость от вендора, сложности кастомизации

**Недостатки, ограничения, риски**

Технические ограничения:
Производительность АБС - система не может обрабатывать более 100 concurrent запросов
Монолитная архитектура интернет-банка - сложности с независимым развертыванием
Устаревшие технологии (Delphi, .NET Framework) - ограничивают выбор инструментов интеграции

Архитектурные риски:
Единая точка отказа - сервис депозитов становится критическим компонентом
Митогация: Кластеризация, актив-активная конфигурация в двух ЦОД
Сложность отладки распределенной системы
Митогация: Внедрение centralized logging и distributed tracing
Синхронизация данных между АБС и сервисом депозитов
Митогация: Четкие правила согласованности, механизмы ресинхронизации

Операционные риски:
Недостаток экспертизы в распределенных системах у команды
Митогация: Обучение, привлечение консультантов, поэтапное внедрение
Сопротивление изменениям со стороны команды АБС
Митогация: Вовлечение в процесс проектирования, демонстрация выгод

Бизнес-риски:
Невыполнение сроков MVP (6 месяцев)
Митогация: Agile подход, приоритизация функциональности, регулярные демонстрации
Низкое adoption нового канала клиентами
Митогация: Маркетинговая кампания, упрощение UX, обучение сотрудников отделений

Компенсирующие меры:
Поэтапный rollout функциональности
Мониторинг производительности в реальном времени
План отката к старому процессу на первые 3 месяца
